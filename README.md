# Lapis CI

`lapismd/lapis-ci` defines the shared, deterministic Linux CI toolchain used by
LapisMD repositories. It provides Node, pnpm, Playwright with Chromium, mdBook, GitHub CLI,
and the browser/system utilities required by package and Storybook validation.

The shared image deliberately does not contain an application's source,
`node_modules`, credentials, or repository-specific dependencies. A consuming
repository may extend the image with a lockfile-specific `pnpm fetch` layer and
must still run a frozen install in its checked-out workspace.

## Pinned toolchain

| Tool                    | Version                      |
| ----------------------- | ---------------------------- |
| Node                    | 24.15.0                      |
| pnpm                    | 10.34.5                      |
| Playwright and Chromium | 1.61.1                       |
| mdBook                  | 0.5.4                        |
| GitHub CLI              | 2.102.0                      |
| Platforms               | `linux/amd64`, `linux/arm64` |

[`versions.json`](./versions.json) is the machine-readable source of truth.
The repository check fails when the Dockerfile or workflows drift from it.
GitHub CLI and mdBook downloads use architecture-specific SHA-256 checksums.
The image smoke test checks each tool's exact version. GitHub CLI supports
package release records and registry dispatch; authentication is supplied only
at job runtime.

## Local validation

```bash
pnpm verify
pnpm image:build
pnpm image:smoke
```

`pnpm image:build` targets the Docker host's native architecture. Use
`pnpm image:build:amd64` to match GitHub-hosted Linux runners or
`pnpm image:build:arm64` for an explicit Apple Silicon build, then run the
verifier against the matching candidate tag.

## Turbo remote cache

LapisMD repositories share task outputs through the authenticated remote cache
instead of uploading `.turbo` through GitHub Actions cache artifacts. The
shared image does not contain credentials or Turbo itself; each consumer uses
its pinned workspace Turbo version and receives cache configuration at runtime.

The organization-level contract is:

| GitHub setting                     | Kind             | Purpose                               |
| ---------------------------------- | ---------------- | ------------------------------------- |
| `TURBO_API`                        | Actions variable | Self-hosted cache API URL             |
| `TURBO_TEAM`                       | Actions variable | Shared LapisMD cache namespace        |
| `TURBO_TOKEN`                      | Actions secret   | Cache-server authentication           |
| `TURBO_REMOTE_CACHE_SIGNATURE_KEY` | Actions secret   | HMAC integrity for uploaded artifacts |

Restrict both secrets to the selected LapisMD repositories that run Turbo.
Fork pull requests do not receive the secrets and must remain able to execute
all tasks normally without remote-cache access. See
[`docs/remote-turbo-cache.md`](./docs/remote-turbo-cache.md) for the consumer
configuration and rotation procedure.

## Publication

Publication is manual. Run the **Publish Lapis CI image** workflow with an
immutable calendar version such as `2026.08.1` and the approval phrase shown by
the workflow. The workflow publishes one multi-architecture manifest with an
SBOM and provenance attestation.

Consumers must use the reported digest:

```yaml
container:
  image: ghcr.io/lapismd/lapis-ci@sha256:<digest>
```

Do not consume `latest` or another mutable tag in CI.

## Dependency-image input receipts

The source-owned `actions/dependency-identity` composite action computes a
receipt for an already prepared dependency-only Docker context. Pin the action
to a reviewed commit. It binds the shared toolchain digest, both target
platforms, every permitted file's path/content/mode and directory modes, then
emits a full SHA-256 identity and lookup tag.

The separate `actions/resolve-dependency-image` action computes current inputs
and verifies the immutable multi-architecture image's signed receipt. A missing
or unavailable cache returns the reviewed toolchain digest; every result still
requires a frozen install. Invalid provenance fails instead of using the image.
Neither helper publishes images or changes consumer pins. Source migrations
must qualify their producer and cold/warm paths first. A lookup tag is never
sufficient authority to run an image. See
[the receipt contract](docs/dependency-image-receipts.md).

`actions/publish-dependency-image` owns the shared build/attest/promote sequence.
The source workflow retains its Dockerfile, dependency context, main-only
serialization and registry/OIDC authority. Existing verified identities reuse
their bytes. Cold publication builds a staging tag, signs its complete input
receipt, verifies it, and promotes the exact index only after reconciliation.
No image-pin PR is generated by this helper.

`actions/setup-gh` installs the image's checksum-verified GitHub CLI on a host
runner. `actions/setup-image-tools` installs the exact host controller versions
in `host-tools.json`; those tools are separate from the shared image contents.

## Source-owned version runtime guard

`actions/guard-version-runtime` validates installed Changesets bytes and a
consumer's exact source-owned version recipe inputs on Node24, before the
consumer mints its writer App token. Pin the action to a reviewed commit and
retain the existing install, command/configuration, releasability, approval and
publication boundaries. The helper does not execute or replace a recipe, install
Deno, select a different formatter or grant write authority.

The reviewed data in `changesets-runtime.json` supports existing CLI2.31.1 and
3.0.3 without a major migration. Source data binds every direct package JS module
and package metadata, rather than trusting a tiny executable shim alone. A
consumer qualification file binds its exact Changesets config, pnpm version,
named commands and selected recipe source files. New lifecycle hooks, changed
inputs, unreviewed CLI versions and root/ancestor Deno formatter declarations
require owning-source requalification.

This is a bounded input guard, not proof that arbitrary scripts or transitive
dependencies are portable. Actual whole-recipe qualification remains separate.
The manual main-only `qualify-version-recipe.yml` workflow executes an immutable
Plugins source with a genuine pending changeset and existing read-only workflow
token for changelog reads. It creates no writer App, source branch or package
publication. See [the runtime contract and qualification procedure](docs/versioning-runtime.md).
